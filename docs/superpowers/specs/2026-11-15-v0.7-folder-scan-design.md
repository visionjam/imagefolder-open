# v0.7 文件夹扫描与容量上限设计

- 日期：2026-11-15
- 状态：已实现（用户要求先跑 v0.7）
- 基线：v0.6.0（`feat/v0.6.0`）
- 分支：`feat/v0.7.0`

## 目标

1. 让原版停更后散落在图库里的存量图片可以被找回来：选择一个 SAF 文件夹，递归找出所有含隐藏内容的 PNG / JPEG / WebP 图片。
2. 扫描只读取载体头部并跳过载荷，不把整张大图读入内存。
3. 扫描过程显示进度并可取消；结果可一键加入现有提取流程。
4. 打包载荷设 256 MB 硬上限，并在打包页显示已选文件大小，避免用户触到 OOM 才知道。

## 非目标

- 不扫描整个 MediaStore 图库（先用 SAF 目录，避免申请媒体权限）。
- 不做流式打包/提取重构；256 MB 上限是当前版本的明确边界。
- 不新增压缩格式，不做 RAR。
- 不做 F-Droid / IzzyOnDroid。

## 实现

### `core/CarrierProbe`

`CarrierProbe.probe(InputStream): CarrierProbeResult?`：

- 先读 12 字节前缀识别 PNG / JPEG / WebP，再用 `PushbackInputStream` 放回前缀继续解析。
- PNG：跳过 8 字节签名，按 chunk 遍历；遇到 `tpWj` 只读前 4 KB 解析 JSON 头，其余用 `skip` 跳过；到 `IDAT` / `IEND` 停止。旧格式按 `tpWj` 数量计条目。
- JPEG：按 marker 遍历；遇到 APP15 且以 `IFBJ` 开头时解析第一个分片的 JSON 头，其余段跳过；到 SOS/EOI 停止。
- WebP：按 RIFF chunk 遍历；遇到 `IFBW` 只读前 4 KB，其余跳过；注意奇数长度补 1 字节。
- 返回 `format`、`name`、`entries`、`encrypted`、`compressed`；没有隐藏内容返回 null；损坏数据不抛异常。
- `HiddenPayloadCodec.parseHeader` 抽出只解析 JSON 头的函数，不复制载荷字节。

### `data/FolderScanner`

- `DocumentFile.fromTreeUri` 递归收集 PNG / JPEG / WebP。
- 扫描前先收集完整列表，用于进度总数；按文件名排序。
- 每张图用 `CarrierProbe` 探测；`shouldContinue` 为 false 时提前返回已找到的结果。
- 返回 `ScanHit(uri, name, size, format, entries, encrypted)`。

### ViewModel / UI

- `ExtractUiState` 增加 `scanning`、`scanScanned`、`scanTotal`、`scanHits`、`scanFolderName`。
- 提取页新增「扫描文件夹」按钮；扫描中显示进度和取消；扫描完成后列出命中项，提供「全部加入提取」。
- 「全部加入提取」复用 `resetExtractForNewSources`，之后走原有提取流程。
- 打包页显示已选文件大小；`buildEntries` 累计超过 256 MB 时抛出明确错误。

## 测试

- `CarrierProbeTest`：PNG / JPEG / WebP 的 IFB2 元数据、旧 PNG 多 chunk 计数、普通图片返回 null、5 MB 载荷只读少量字节。
- JVM 测试总数 60。
- 扫描 UI 和真实文件夹需要真机手动验证。

## 已知限制

- SAF 目录遍历速度取决于提供方；超大目录可能需要等待。
- 扫描结果显示的是头部元数据；加密包的条目数来自明文头，内容仍需密码才能解开。
- 256 MB 是当前内存模型的硬上限，不是流式实现。
