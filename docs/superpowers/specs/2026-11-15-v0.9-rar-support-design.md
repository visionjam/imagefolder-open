# v0.9 RAR 解压支持设计

- 日期：2026-11-15
- 状态：实现中
- 基线：v0.8.0（`feat/v0.8.0`）
- 分支：`feat/v0.9.0-rar`

## 背景

提取结果中的 ZIP、7z、TAR、GZ、BZ2、XZ 已经可以在应用内解压，但 RAR 只做识别并提示“暂不支持”。
RAR 是分享场景里常见的格式，用户需要在不离开应用的情况下打开它。

## 许可证调研与决策

项目以 GPL-3.0 分发，RAR 解压库必须与 GPL-3.0 兼容。调研了三条路线：

| 方案 | 能力 | 许可证 | 结论 |
| --- | --- | --- | --- |
| junrar 8.x | RAR4/5/7、分卷、密码、加密头 | unRAR freeware（非 OSI，带使用限制） | ❌ 与 GPL-3.0 不兼容 |
| 7-Zip-JBinding | RAR4/5、分卷、密码 | LGPL-2.1 + unRAR restriction | ❌ 同样卡在 unRAR；Android 分支停留在 2016 年引擎，含已知 RAR CVE |
| libarchive | RAR5（含固实/分卷）、非固实 RAR4 | BSD-2-Clause | ✅ GPL-3.0 兼容 |

**决策：使用 libarchive。** 接受它的能力边界：不支持 RAR 密码/加密头，不支持固实 RAR4。
如果以后必须支持加密 RAR，需要单独做许可证评估（GPL-3.0 §7 链接例外或独立进程方案），不在本版本范围内。

## 目标

1. 无密码 RAR5 单卷、固实、分卷都能解压。
2. 无密码、非固实的 RAR4 单卷和分卷能解压。
3. 旧式 `.rar` + `.r00`… 与新式 `.part1.rar`… 分卷都能识别、排序、报告缺失。
4. 复用现有解压 UI、路径安全、条目数/总大小限制和临时目录清理。
5. 加密 RAR、固实 RAR4 给出明确的中英文提示，而不是泛化的失败。

## 非目标

- RAR 密码与加密头。
- 固实 RAR4。
- 创建 RAR 压缩包。
- ISO / CAB / DEB / RPM、ZSTD。
- 自动在设备上搜索缺失分卷（仍要求所有分卷都在当前提取结果中）。

## 实现

### 架构

`ArchiveExtractor` 保持单入口，新增可替换的 `RarExtractor` 接口：

- `LibarchiveRarExtractor`：生产实现，调用 `me.zhanghai.android.libarchive`。
- JVM 单测通过 `ArchiveExtractor.rarExtractorOverride` 注入假实现，避免测试环境加载 Android native 库。

`LibarchiveRarExtractor` 的流程：

1. 把单卷字节或分卷列表写入临时目录；分卷保留原文件名并按 `splitGroup` 的顺序传入。
2. `Archive.readNew()` + `readSupportFormatRar` + `readSupportFormatRar5`。
3. `Archive.readOpenFileNames(paths, 64 KiB)`。
4. 先查 `readHasEncryptedEntries`；再逐条检查 `isDataEncrypted` / `isMetadataEncrypted`，命中即抛
   `ArchiveUnsupportedException(RAR_ENCRYPTED)`。
5. 目录记空条目；普通文件用直接 `ByteBuffer` 循环 `readData` 读取，读到 0 即 EOF；其他类型（符号链接等）跳过。
6. 读取过程中调用现有 `ExtractionLimits`，沿用 100,000 条目 / 512 MB 上限。
7. 返回后由 `ArchiveExtractor.normalizeRarEntries` 统一做路径安全校验。

### 分卷命名

`parseSplitName` 新增两个族：

- `RAR_OLD`：`archive.rar` 为第 0 卷，`archive.r00` 为第 1 卷，依此类推。
- `RAR_NEW`：`archive.partN.rar`，支持 `part1` 和 `part01` 两种补零写法，缺失名沿用原补零宽度。

单卷 `.rar` 或单个 `.part1.rar` 不返回分卷组，走普通 `extract`。

### 错误映射

`mapRarFailure` 把 libarchive 的错误文本映射为现有异常：

- `Encryption is not supported` / `Reading encrypted data is not currently supported` /
  `RAR encryption support unavailable` → `ArchiveUnsupportedException(RAR_ENCRYPTED)`。
- `RAR solid archive support unavailable` → `ArchiveUnsupportedException(RAR4_SOLID)`。
- `Unexpected end of volume` / `truncated` → `ArchiveFormatException("RAR 分卷不完整")`。
- 其他 → `ArchiveFormatException`。

`MainViewModel` 按 `ArchiveUnsupportedReason` 选择中英文字符串。

### 依赖

Android 封装使用 `app/libs/libarchive-android-1.1.6-libarchive-3.8.8.aar`：

- Java 绑定：`me.zhanghai.android.libarchive:library:1.1.6`，`minCompileSdk=1`，与项目
  `compileSdk 35` / AGP 8.7.3 兼容。
- native 库：`library:1.1.7` 的 `libarchive-jni.so`（libarchive **3.8.8**）。1.1.6 自带的
  libarchive 3.8.1 存在 2026 年已修复的 RAR5 CVE，不使用。
- 1.1.6 与 1.1.7 的 Java API 和全部 JNI native 方法签名逐项比对一致，因此可安全混用。
- 1.1.7 直接依赖要求 `compileSdk 37.2`，会迫使整个项目升级 AGP/Gradle，风险与本功能无关，故不采用。

复现脚本见 `scripts/repack-libarchive-aar.sh`。

### 体积与 ABI

libarchive 的 `.so` 不压缩打包，四个 ABI 共约 9.7 MB。release 只保留
`arm64-v8a` / `armeabi-v7a`，release APK 从约 2.9 MB 增至约 7.0 MB。
需要 x86 模拟器时在 `app/build.gradle.kts` 的 `ndk.abiFilters` 中加回。

## 已知限制

- 加密 RAR 不支持；提示“暂不支持加密的 RAR 压缩包”。
- 固实 RAR4 不支持；提示“暂不支持固实 RAR4 压缩包”。
- 分卷必须全部出现在当前提取结果中。
- libarchive 的 RAR 读取器历史上 CVE 较多，依赖已固定在 3.8.8；升级依赖时应优先选择包含最新
  RAR 修复的版本。
- 未在真机上验证 RAR 解压；首次真机测试应覆盖上述 instrumentation 用例。
