# v1.0.0 分卷图种设计

- 日期：2026-11-17
- 状态：已实现，待真机实测
- 相关代码：`core/SplitCarrierCodec.kt`、`MainViewModel.generate/scanSources`、`ui/PackScreen.kt`、`ui/GeneratedImageScreen.kt`
- 格式文档：[docs/FORMAT.md](../../FORMAT.md)

## 1. 问题

一份图种 = 一张正常图片 + 藏在私有 chunk / APP 段里的完整归档。载荷上限 64 MB，
加上表图本身，单张图片可能达到几十 MB。聊天软件、论坛和图床普遍限制单图大小
（常见 5 MB / 10 MB / 20 MB），直接上传会被拒绝或重新压缩。

需求：把一份完整图种拆成 1–9 张「小图种」，每张都能单独上传，接收方全部拿到后仍能
还原出原来的内容。

## 2. 方案

不拆图片像素，而是拆**封装数据**：

1. 打包流程先照旧生成一个 `IFB2` 封装（ZIP，可选压缩 / 加密）。
2. 按份数把封装等分成 N 段。
3. 每段加上 60 字节 `IFSP` 段头，写进一张独立的表图副本。
4. 每张输出图仍是合法 PNG / JPEG / WebP，可直接查看、上传。

提取时：

1. 扫描用户选中的所有图片，识别 `format = "ifsp"` 的载荷。
2. 按 8 字节随机组号 `groupId` 分组。
3. 检查组内序号 0..count-1 是否齐全；逐份校验 CRC32。
4. 按偏移拼回封装，校验整包 SHA-256。
5. 交给原有 `BundleCodec.unpack`，加密包照常要密码。

## 3. 格式

### 3.1 JSON 头

沿用 `JSON 头 + 0x00 + 数据` 布局，新增两个字段：

```json
{"name":"图片文件夹.zip","mime":"application/zip","format":"ifsp","enc":false,"comp":true,"entries":12,"part":2,"parts":5}
```

- `part` / `parts` 从 1 开始，方便直接展示「第 2/5 份」
- 旧版本读到未知字段会忽略（`ignoreUnknownKeys`），不会崩

### 3.2 IFSP 段头

固定 60 字节，大端序：

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 4 | magic | `IFSP` |
| 4 | 1 | version | 1 |
| 5 | 1 | flags | 0，保留 |
| 6 | 1 | index | 0 起 |
| 7 | 1 | count | 1–9 |
| 8 | 4 | totalLength | 完整封装长度 |
| 12 | 4 | offset | 本段在封装中的起点 |
| 16 | 8 | groupId | 随机组号 |
| 24 | 32 | envelopeSha256 | 完整封装 SHA-256 |
| 56 | 4 | sliceCrc32 | 本段 CRC32 |
| 60 | n | slice | 数据段 |

校验规则：

- `count ∈ 1..9`、`index < count`
- `offset == index * ceil(totalLength / count)`
- `sliceLength == min(sliceSize, totalLength - offset)`
- CRC32 必须匹配；重组后再验 SHA-256

## 4. 交互

### 4.1 打包页

- 选项区新增「分卷输出（1–9 张）」步进器，默认 1（关闭）
- 选择 >1 时显示提示：分卷使用新版格式；表图最长边限制 1280 px
- 分卷强制走 `IFB2` 封装；PNG 基础兼容模式（逐文件 `tpWj`）不参与分卷

### 4.2 结果页

- 预览第一份
- 标题下显示「共 N 份，合计 X MB」
- 逐份列出文件名、大小、是否已保存
- 按钮变为「保存全部 N 张」；分享使用 `ACTION_SEND_MULTIPLE`
- 改名会同步更新所有未保存份的文件名（`-1of5` 后缀）

### 4.3 提取页

- 扫描结果对分卷图片显示「分卷 2/5」徽标
- 只选中部分份数时提示缺哪几份，不产生半截文件
- 多组同时不完整时提示组数
- 完整组自动重组、解包，结果与普通图种一致
- 加密分卷在缺密码 / 密码错误时复用原有密码弹窗

## 5. 边界与取舍

- **只在打包时拆分**：v1.0.0 在生成阶段把封装切分。对已经生成好的单张图种做「事后拆分」
  需要先剥离原 `tpWj` / APP15 / `IFBW` 载荷，再用原图作表图重新嵌入，留作后续工作。
- **每份都重复表图**：这是拆分的固有成本。若表图本身接近平台上限，拆分不会让单张变小，
  因此分卷模式把表图最长边压到 1280 px，并在 README 写明适用场景。
- **份数上限 9**：产品约束，UI 与格式都按 1 字节存份数；后续放宽只需改常量与 UI。
- **顺序无关**：组号与序号都在图内，平台改文件名不影响重组。
- **重复份**：同一张图被选两次时按序号去重；不同数据却声明同一序号会在重组时报重复。
- **跨组混用**：组号不同直接拒绝，避免把两次打包的片段拼在一起。
- **兼容性**：`ifsp` 只有本应用识别；原版 / 其他工具会把每份当作不完整的 `.zip`。
  这与现有 `IFB2` 的兼容性定位一致。
- **内存**：拆分时封装已在内存中，分片是额外副本；仍受 64 MB 载荷上限约束。

## 6. 安全

- 组号使用 `SecureRandom`，不携带时间、设备或用户信息。
- 段头只包含长度、序号、随机组号与哈希，不泄露文件名（文件名在加密包的 ZIP 内）。
- CRC32 只用于发现传输损坏；完整性以 SHA-256 为准。
- 不新增权限、不联网，符合项目不变量。

## 7. 测试

JVM（`SplitCarrierCodecTest`，13 个用例）：

- 1–9 份拆分 / 重组往返
- 任意顺序重组
- 缺份报告（序号）
- 跨组混用、重复份拒绝
- 分片 CRC 损坏、整包 SHA-256 不匹配拒绝
- 极小封装不产生空份
- 非分卷载荷不误判
- 文件名规则
- PNG / JPEG / WebP 三种载体分卷往返
- 加密封装拆分后仍需正确密码
- `CarrierProbe` 能读出分卷元数据

真机待测（v1.0.0 发版前）：

- 打包 3 份 / 9 份，逐张保存与一次性分享
- 相册多选全部份数提取；只选部分份数时的提示
- 加密分卷的密码流程
- 分卷图片在系统相册、聊天软件预览正常
