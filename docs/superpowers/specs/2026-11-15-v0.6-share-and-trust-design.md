# v0.6 分享入口与信任可见设计

- 日期：2026-11-15
- 状态：范围已在对话中确认（「上吧」，分发暂缓）
- 基线：v0.5.1（`dfa6ca8`）
- 分支：`feat/v0.6.0`

## 背景与意图

项目定位是原版「图片文件夹」的开源继任者，但格式的读写两端实际上都锁在本 App 里：新生成的图片，对方不装本 App 就打不开。v0.6 不做网页提取器，先把 App 接进 Android 的分享动线，并把「纯本地、无网络权限、开源」的信任写清楚，让它在日常使用里更像一个工具，而不是一个必须先打开的目的地 App。

用户明确暂缓 F-Droid / IzzyOnDroid 等分发工作。

## 目标

1. 从其他 App 分享文件或图片到本 App：普通文件默认作为载荷；图片若检测到隐藏内容，让用户选择「提取」或「作为载荷打包」。
2. 生成结果可以直接分享；首次分享提示聊天/社交平台重压缩图片的风险。
3. 关于页、README、`SECURITY.md` 三处把信任说清楚：无网络权限、无统计、纯本地处理、加密保护什么/不保护什么。
4. 新包 PBKDF2 迭代从 150,000 提升到 600,000；旧包继续可读。
5. 版本号 0.6.0（versionCode 7），补齐更新日志。

## 非目标

- 不做图库/目录扫描（留给 v0.7）。
- 不做流式大文件重构；保留现有内存模型，只把限制写清楚。
- 不做 F-Droid / IzzyOnDroid 元数据或上架。
- 不新增网络权限，不引入统计或崩溃上报。
- 不改变 `tpWj` / `IFB2` 的二进制布局。

## 反目标

- 不把 App 扩成通用解压工具；不新增压缩格式。
- 不为了分享方便而降低加密默认值，不保存密码。
- 不把「隐藏内容的存在」说成加密保护的一部分。

## 行为设计

### A. 接收分享

- `MainActivity` 增加 `android:launchMode="singleTop"`，并注册 `ACTION_SEND` / `ACTION_SEND_MULTIPLE`（`mimeType="*/*"`）。
- `onCreate` 只在 `savedInstanceState == null` 时处理启动 Intent，避免配置/进程重建时重复导入；`onNewIntent` 每次都处理，并先 `setIntent(intent)`。
- URI 来源依次取 `Intent.EXTRA_STREAM`、`ClipData`；只带 `EXTRA_TEXT` 的分享提示「没有可读取的文件」。
- 用 `UriUtils.describe` 解析名称/大小/MIME；读不出的条目跳过并提示数量。
- 检测隐藏内容：仅对图片且大小 ≤ 64 MB（或大小未知）的文件读取字节并调用 `CarrierCodec.extractItems`；更大的文件直接当作载荷，避免 OOM。检测在 `Dispatchers.IO` 执行。
- 若至少一张图片含隐藏内容：显示选择对话框
  - 「提取隐藏内容」只用含隐藏内容的图片，切到提取页并填入 sources。
  - 「作为载荷打包」把全部分享项加入打包页。
  - 「取消」丢弃本次分享。
- 若没有图片含隐藏内容：全部加入打包页，切到打包页，提示「已添加 N 个文件」。
- 标签页状态从 `ImageFolderApp` 的 `rememberSaveable` 提升到 `MainViewModel.activeTab`，让分享处理可以切换页面；配置变化仍由 ViewModel 保持。
- 待处理分享放在 ViewModel：`PendingShare(extractUris, packUris, names)`。若对话框已存在又收到新分享，按 URI 去重合并。

### B. 生成结果分享

- `GeneratedImageScreen` 增加「分享」按钮。
- 把 `result.bytes` 写入 `cacheDir/shared/<fileName>`，用现有 FileProvider（`${applicationId}.fileprovider`）生成 URI，发 `ACTION_SEND`，类型用 `result.mime`，加读权限 flag。
- 首次分享弹出提示对话框：聊天/社交平台可能重新压缩或剥离未知数据块，建议以「文件」形式发送。提供「不再提示」，状态存 `SharedPreferences`；按钮为「继续分享 / 取消」。
- 写缓存或分享失败时用 snackbar 提示。

### C. 信任面

- 关于页新增「隐私与信任」卡片（放在「设置」之后、「实用功能」之前）：
  - 无网络权限；不收集任何数据；所有处理留在本机。
  - 「检查更新」只是打开浏览器。
  - 开源 GPL-3.0，格式有公开文档。
- `README.md` 与 `README.zh-CN.md` 增加 Privacy / 隐私一节，内容与关于页一致，链接 `SECURITY.md` 与 `docs/FORMAT.md`。
- 新增根目录 `SECURITY.md`：
  - 保护：加密载荷的内容与内层文件名；没有密码无法解开。
  - 不保护：隐藏数据的存在、`enc`/`comp`/`entries` 等明文标志、外层通用文件名、载体图片本身。
  - 传输风险：平台重压缩可能剥离数据块；建议以文件发送。
  - 密码丢失不可恢复。
  - 漏洞报告走 GitHub Security Advisories，不走公开 issue。

### D. 加密参数

- `BundleCodec.PBKDF2_ITERATIONS` 从 `150_000` 改为 `600_000`。
- 读取端本来就从头部读取迭代数（`MIN_ITERATIONS=10_000`、`MAX_ITERATIONS=1_000_000`），旧包不受影响。
- 更新 `docs/FORMAT.md`、两份 README 中出现的 150,000；更新 CHANGELOG。
- 单元测试：
  - 新加密包的头部迭代数等于 600,000。
  - 手工构造的 150,000 次加密信封仍能解密（验证向后兼容）。

### E. 版本与文档

- `versionCode = 7`，`versionName = "0.6.0"`。
- CHANGELOG 增加 v0.6.0 节。
- README 版本行更新。
- 不做分发相关改动。

## 边界情况

- 只分享文本、没有流：提示后不改变页面。
- 文件提供方不支持 seek/临时授权：按普通 URI 处理；分享授权在 Activity 存活期间有效。进程死亡后状态丢失，可接受。
- 同一 URI 重复分享：去重。
- 大图片超过 64 MB：不检测隐藏内容，按载荷处理。
- 分享加密图片：检测只看头部，能识别 `enc`；提取时仍走密码流程。
- 连续两次分享：合并到当前待处理列表。
- FileProvider 写入失败：snackbar，不崩溃。

## 测试与验证

- `./gradlew testDebugUnitTest` 全部通过（新增 KDF 用例）。
- `./gradlew assembleDebug` 成功。
- 真机手动验证：
  - 从「文件」/相册分享一个普通文件 → 打包页出现该文件。
  - 分享一张本 App 生成的图片 → 出现「提取 / 打包」选择，提取能得到原载荷。
  - 生成结果页点分享 → 首次出现平台风险提示，继续后系统分享面板出现。
- 不新增网络权限（检查合并后的 Manifest）。
